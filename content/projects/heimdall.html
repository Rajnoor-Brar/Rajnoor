In short

Heimdall runs Monte Carlo studies in high-energy physics. A TOML file names a chain of tools (an event generator, Rivet, your own programs, the plotter) and the settings to sweep. Heimdall plans every point, runs each tool as its own supervised process, refuses to call a truncated result complete, reruns only what changed, and scores the resulting curves against measured data. It is the third design of a framework I started for my own studies. It is open source and still in active development.

The problem

A phenomenology study tends to look the same every time. You generate events with Pythia, Sherpa or Herwig, analyse them with Rivet, compare the histograms with a published measurement, and repeat for every PDF set, beam energy and tuning parameter worth trying. Done by hand, this becomes a pile of shell scripts and copied cards. A sixteen-point sweep dies at point nine on a typo. A generator that crashes mid-stream leaves a histogram that looks complete. Two weeks later, nobody can say which card made which curve.

The first version was exactly that pile: four scripts around Pythia → FIFO → rivet and a ten-thousand-line C++ utility layer. The second was a Python orchestrator around one in-process C++ event loop. Heimdall is the third. It kept what the first two learned and rebuilt everything around a single idea.

The model: tools are processes, chained by a TOML

The runner decides; the tools do the physics. No tool runs inside another, the runner links no physics library, and no tool ever reads the TOML. Physics stays in each tool's native card (a Pythia .cmnd, a Sherpa YAML). A swept setting is rendered as an override into that point's card, and each tool merges it by its own rule.

A study lives in its own work dir, usually its own git repository. An errand file declares the tools, the quantities that can vary, and named configurations that pick which ones do. This one is abridged from Brookhaven, the photoproduction study that runs on Heimdall: 

[errand]
name   = "photoproduction"
events = 1_000_000
# an inner list runs together, joined by a FIFO
chain  = [["@generator", "rivet"], "yd2rt"]

# a quantity whose values are whole tools
[quantities.generator]
points = [
  { tag = "py8", value = "pythia" },
  { tag = "sh3", value = "sherpa" },
]

# E_e x E_p in GeV: eight EIC beam settings
[quantities.energies]
points = [
  { tag = "18x275", value = [18, 275] },
  { tag = "5x130",  value = [5, 130] },
  # … six more
]

[cfgs.generator_energies]
vary = ["generator", "energies"]   # 2 x 8 = 16 points

heimdall run eic/photoproduction generator_energies expands that into sixteen points. For each one it writes a finished card and command line (seeds are numbers, paths are absolute, threads = 0 is already a count), and --plan prints exactly what would run before anything does.

What can go wrong, and what it does about it

A chain joined by FIFOs fails in two ways a single process never does, and Heimdall handles both by construction rather than by retry.

  • Deadlock at open. A FIFO blocks until both ends are open. If the writer dies before opening its end, the reader waits for ever and never gets a SIGPIPE. So every tool runs in its own process group. The first nonzero exit is taken as the cause, and the rest of the group gets SIGTERM, then SIGKILL. A tool that stays silent past its stall_after counts as failed. A death by SIGPIPE is treated as a consequence, never the cause.
  • A partial result that looks complete. If the generator crashes mid-stream, Rivet simply sees end-of-file and exits 0. So the consumer's event count is checked against the producer's, every product keeps a .partial name until its checks pass, and .complete is written last. A failed point leaves its products under partial names, the rest of the run goes on, and the next run resumes exactly there.
  • Refuse early, and say what to do. Every check runs before any process starts, and every refusal names the file, the key, and a fix. A swept quantity that no tool consumes, a Rivet option that is not declared, or a card that sets one key twice is an error at plan time, not a silent no-op discovered from the plots.

Reruns by identity, not by folder

Each point has an identity, a hash of what actually decides its result: the resolved cards and command lines, each executable's own hash, the event count and the seed rule. Folder names and plot settings are deliberately left out, so moving a study reruns nothing and restyling a page only redraws it. Rerunning an unchanged study does nothing; changing one setting reruns exactly the points it touches, and --why shows the difference. An opt-in points library pools generation across studies, so two errands that ask for the same physics run it once. Because the identity is load-bearing, a golden-file test pins it: an accidental change shows up as a failing test, not as a silent full rerun.

Scoring curves against data

When a sweep has reference data, every drawn page (one observable at one point) is compared with it on eleven metrics, grouped into categories: statistical compatibility, normalisation, shape, trend across the axis, local defects (spikes and holes), and integrity. Each metric is hinged between a good and a bad threshold that belongs to the metric itself, so a curve's loss never changes because other curves were added to the pool. Category costs are combined by root mean square, so one bad category shows instead of being averaged away. Points are then ranked, and marginals ask which value of each swept setting is best on average: each point is compared only with points identical to it in every other setting, using trimmed means.

Every summary prints how its own numbers were made: thresholds, weights, gates, tie rule, and one real row worked through by hand. The engine is opinionated, and the open questions are written down with it. One of them: with gates off, the default, a broken point's noise can make a real effect read as indistinguishable in the marginals. That is a known open issue, not a hidden one.

What it refuses to do

The design documents record each principle with what it buys and what it costs. For example, running every tool as a separate process costs about 10 % of the old in-process throughput end to end (measured), in exchange for any program in any language joining a chain just by being an executable. They also list what is refused outright:

RefusedWhy
A general DAG or workflow engineA chain is a sequence of groups; the connection rules only check it.
Physics in the TOMLIt lives in each tool's native card, the card on disk is the card that ran, and there is no cross-generator dialect to re-verify on every release.
Inferring connections, units, data maps, or which tool a setting is forA wrong guess looks plausible. The previous version drew ZEUS data over the wrong observable this way.
Silently ignoring a key a tool cannot honourIt is an error, with the file and line.
CMakemake <path>.exe is the whole build interface.

The stack underneath

Heimdall also builds the software it runs on: ROOT, Pythia 8, Herwig 7, Sherpa 3, Whizard, MadGraph5, Rivet, YODA, Delphes, FastJet, HepMC3, LHAPDF and Geant4. They are built from source or taken from conda, as toolkits described in plain TOML files, with patches kept beside the recipes, a container image for clusters, and heimdall doctor to check what the installed stack can actually do. Pages are drawn by a small ROOT program (Paint, C++) or by matplotlib.

Status

Heimdall is research software in active development, not a release. The current design dates from late September 2026, and it moved into its own repository in October. It is about 35,000 lines of Python with roughly 2,400 test cases and a C++ plotting app. Its reference docs are generated from the code, and heimdall docs opens all of it as one searchable page. Still to do: continuous integration (today the full-stack workflow is started by hand), and moving every study to the newest configuration format. The plan for both is tracked in the open, issue by issue, in the repository.
